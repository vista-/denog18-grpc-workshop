gRPC

A framework for calling functions on a remote machine. It runs over HTTP/2, but you never see HTTP: no URLs, no verbs, just named RPCs such as Get, Set or Subscribe. One connection can carry many parallel streams, which is what makes streaming telemetry cheap.

Protocol Buffers

The message format gRPC uses. A schema describes each message, and the data goes over the wire in a compact binary form that is fast to parse and has clients in every common language.

syntax = "proto3";
message InterfaceStats {
  string if_name   = 1;
  uint64 in_octets = 2;
}

YANG

The language that describes what a device can be configured with and what state it reports. Every gNMI path you use today, like /interface[name=ethernet-1/1]/mtu, is a walk through a YANG model.

OpenConfig

Vendor-neutral YANG models written by network operators and published on GitHub. Where they don't cover a feature yet, you fill the gap with the vendor's native models. You will do exactly that in section 2.

Containerlab turns a short YAML file into a running lab of containers and wires them together. Nokia SR Linux, the switch OS in the lab, is modelled in YANG from the ground up, so everything you can do in its CLI you can also do over gRPC.

Section 1 · gNMI

Configure, read and streamgRPC Network Management Interface

gNMI replaces the patchwork of CLI scraping, SNMP polling and syslog parsing with one model-driven interface. It has four RPCs: Capabilities, Get, Set and Subscribe.

1.1

Ask the switch what it supports

Capabilities lists the YANG models and encodings the device understands. A reply also proves that gNMI is up and that your credentials work.

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure cap
You should see
gNMI version: 0.10.0
supported models:
  - urn:nokia.com:srlinux:aaa:aaa:srl_nokia-aaa, Nokia, 2026-07-31
  … several hundred more
supported encodings:
  - JSON_IETF
  - PROTO
  - ASCII
1.2

Read configuration and state with Get

Every request names a path into the YANG tree. Find paths in the Nokia YANG Browser, or let the switch tell you: go to the object in the CLI and ask for its XPath.

leaf1 CLI
interface ethernet-1/1
pwc xpath
You should see
/interface[name=ethernet-1/1]

Now fetch that interface's configuration over gNMI:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path /interface[name=ethernet-1/1] --type config

Leave out --type config and you get operational state, which is gnmic's default. Here is the state of the client-facing port:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path /interface[name=ethernet-1/10]/oper-state
You should see
"updates": [
  {
    "Path": "srl_nokia-interfaces:interface[name=ethernet-1/10]/oper-state",
    "values": {
      "srl_nokia-interfaces:interface/oper-state": "up"
    }
  }
]
1.3

Change one value with Set

Set changes configuration and commits it in the same call. The quickest form packs path, type and value into one argument: path:::type:::value.

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  set --update /interface[name=ethernet-1/10]/mtu:::json:::4000
You should see
"results": [
  {
    "operation": "UPDATE",
    "path": "interface[name=ethernet-1/10]/mtu"
  }
]

The same change with separate path and value, this time over the TLS server on 57400:

VM shell
gnmic -a leaf1 -u admin -p NokiaSrl1! --skip-verify --encoding json_ietf \
  set --update-path /interface[name=ethernet-1/10]/mtu --update-value 3600

Read the MTU back with Get. It should say 3600.

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path /interface[name=ethernet-1/10]/mtu
On the dashboard

In the leaf1 row, Config changed drops to "a few seconds ago", Interface MTU shows the new value for e1-10, and gRPC calls counts your gNMI Set.

1.5

Update or replace? The SNMP experiment

An update merges your data into what is there. A replace deletes everything under the path first, then writes your data, in one commit. Watch the difference with a new SNMP community.

VM shell
# 1. what is configured now
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path /system/snmp --type config

# 2. merge the new community in
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  set --update-path /system/snmp --update-file gnmi/leaf1-snmp.cfg

Run the Get again: both communities are now configured. That is not what we wanted. Replace instead:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  set --replace-path /system/snmp --replace-file gnmi/leaf1-snmp.cfg
You should see
"operation": "REPLACE",
"path": "system/snmp"

A final Get shows only denog-snmpv2-community.

Some platforms lack YANG coverage for a feature. For those, gNMI can carry raw CLI lines too:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  set --update-cli-file gnmi/leaf1-cli.cfg

Get /system/snmp once more: a third community, cli-snmpv2-community, appears.

1.6

Commit confirmed: changes that undo themselves

For a risky change, ask the switch to roll it back unless you confirm it in time. Set the MTU to 8000 with a five-minute safety net:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  set --update /interface[name=ethernet-1/10]/mtu:::json:::8000 \
  --commit-id mtu-8000 --commit-request --rollback-duration 5m

While the timer runs, the switch refuses any other change, from any interface. A logged-in CLI shows [commit confirmed (rollback in a minute)] in its status bar, and another Set fails:

Expected refusal
SetRequest failed: rpc error: code = Aborted desc = Cannot commit transaction (commit confirmed in progress)

Let the five minutes run out, then Get the MTU: it is back at 3600. Now repeat with 7500 and confirm in time:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  set --update /interface[name=ethernet-1/10]/mtu:::json:::7500 \
  --commit-id mtu-7500 --commit-request --rollback-duration 5m

gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  set --commit-id mtu-7500 --commit-confirm

The MTU stays at 7500. Don't want to wait? --commit-cancel rejects a pending commit immediately.

1.8

Subscribe: the four ways to stream

Subscribe is what powers streaming telemetry. The switch pushes data to you instead of you polling it.

ModeWhat the switch sendsGood for
oncethe current value, then it stopsa quick snapshot
samplethe value every intervalcounters, rates
on-changethe value whenever it changesstates: up/down, BGP sessions
target-definedwhatever the YANG model says per leafthe gnmic default
VM shell
# once
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  sub --path /interface[name=ethernet-1/1]/statistics/out-packets --mode once

# every 5 seconds, until Ctrl+C
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  sub --path /interface[name=ethernet-1/1]/statistics/out-packets \
  --mode stream --stream-mode sample --sample-interval 5s
You should see
{ … "interface/statistics/out-packets": "2218" … }
{ "sync-response": true }
{ … "interface/statistics/out-packets": "2218" … }   ← 5 s later, and so on

sync-response marks the end of the initial snapshot. Everything after it is a change on top of that state.

1.9

See on-change react to traffic

Start an on-change subscription and keep it running:

VM shell · window 1
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  sub --path /interface[name=ethernet-1/1]/statistics/out-packets \
  --mode stream --stream-mode on-change

Very little arrives, because the counter barely moves. In a second window, make it move:

leaf1 CLI · window 2
ping 192.168.10.3 network-instance default -i 1

Now an update arrives every second. Stop the ping and the stream goes quiet. Try -i 0.1: updates still come once per second, because telemetry can only be as fresh as the switch updates its own data model.

1.10

Watch a link go down

With no stream mode given, SR Linux picks per leaf. For oper-state that means on-change:

VM shell · window 1
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  sub --path /interface[name=ethernet-1/10]/oper-state --mode stream
VM shell · window 2
docker exec -it client1 ip link set dev eth1 down
docker exec -it client1 ip link set dev eth1 up
You should see
"interface/oper-state": "up"
{ "sync-response": true }
"interface/oper-state": "down"    ← the moment you take eth1 down
"interface/oper-state": "up"
On the dashboard

Port 10 of leaf1 turns red on the front panel and in the topology, and green again when you bring eth1 back.

Paths can be wildcards too. /interface[name=ethernet-*]/oper-state streams every Ethernet port, and --path /interface[name=ethernet-1/10] streams the whole subtree, counters included.

Section 2 · gNMI with OpenConfig

Build the fabric with vendor-neutral modelsOpenConfig where it exists, native models where it doesn't

Same gNMI, different YANG models. You will read the switch through OpenConfig, then configure BGP and an EVPN-VXLAN service with a mix of OpenConfig and SR Linux models. At the end, the two clients can reach each other.

2.1

Look at the switch through OpenConfig

The SR Linux CLI speaks both model families. enter oc switches to OpenConfig, enter srl switches back; the first line of the prompt tells you where you are, like --{ + oc running }--.

leaf1 CLI
enter oc
info flat interfaces interface ethernet-1/1
You should see
set / interfaces interface ethernet-1/1 config name ethernet-1/1
set / interfaces interface ethernet-1/1 config description To-Spine
set / interfaces interface ethernet-1/1 subinterfaces subinterface 0 ipv4 addresses address 192.168.10.2 config prefix-length 31
…

Over gNMI, prefix the path with openconfig::

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path openconfig:/interfaces/interface[name=ethernet-1/1] --type config

gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path openconfig:/interfaces/interface[name=ethernet-1/1]/state/counters/out-pkts
2.2

Configure BGP and EVPN on all three switches

OpenConfig has no model for VXLAN tunnels yet, so each Set carries two files: OpenConfig for BGP and policies, SR Linux native for the MAC-VRF and VXLAN parts. First confirm there is no BGP yet:

VM shell
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf \
  get --path openconfig:/network-instances/network-instance[name=*] --type config

Then push the configuration. Make sure you completed step 1.4 first: BGP needs the loopbacks.

VM shell · in denog18-grpc-workshop
for sw in leaf1 leaf2 spine; do
  gnmic -a $sw:57401 -u admin -p NokiaSrl1! --insecure --encoding json_ietf set \
    --update-path openconfig:/ --update-file configs/oc/$sw-oc.cfg \
    --update-path srl_nokia:/  --update-file configs/srl/$sw-srl.cfg
done
You should see, three times
"results": [
  { "operation": "UPDATE", "path": "openconfig:/" },
  { "operation": "UPDATE", "path": "srl_nokia:/" }
]

Section 3 · gNOI

gNOI covers the things an operator does to a box rather than configures on it: ping, traceroute, file transfer, health checks, software upgrades, reboots. You'll use the user gnoic1, whose role is allowed to call gNOI and nothing else.

3.1

System time

The simplest gNOI call. If it answers, gNOI works.

3.2

Ping and traceroute from the switch

Your client asks leaf1 to ping leaf2's loopback. The ping runs on the switch and the results stream back.

gnoic -a leaf1:57401 -u gnoic1 -p gnoic1 --insecure \

Back up the configuration

Read on: software upgrades with gNOI (theory, not supported in the container)

On real hardware, an upgrade is three OS RPCs: Verify the running version, Install (transfer) the new image, Activate it and reboot.

VM shell · against hardware
gnoic -a HW-leaf1:57401 -u admin -p NokiaSrl1! --insecure os verify
gnoic -a HW-leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  os install --version srlinux_26.10.1 --pkg ../26.10/srlinux-26.10.1.bin
gnoic -a HW-leaf1:57401 -u admin -p NokiaSrl1! --insecure os activate --version 26.10.1

The optional Ansible exercise, which runs gNOI pings from several switches and reports pass or fail, is in gnoi/README.md section 3.7.

Section 4 · gNSI

Control who may call what, and encrypt the sessiongRPC Network Security Interface

gNSI manages the security of the gRPC services themselves. Authz sets which user may call which RPC. Certz manages the TLS certificates the gRPC servers present. These calls go to the TLS server on port 57400.

4.1

Talk TLS, and see why it fails at first

VM shell
gnoic -a leaf1 -u gnoic1 -p gnoic1 file stat --path /etc/opt/srlinux/config.json
Expected failure
rpc error: code = Unavailable desc = connection error: desc = "transport: authentication handshake failed: tls: failed to verify certificate …"

The switch's certificate was signed by Containerlab's CA, which your VM doesn't trust. Tell the client to skip verification for now. You'll fix this properly in 4.4.

VM shell
gnoic -a leaf1 -u gnoic1 -p gnoic1 --skip-verify file stat --path /etc/opt/srlinux/config.json
gnoic -a leaf1 -u gnoic1 -p gnoic1 --skip-verify file get --file /etc/opt/srlinux/config.json --dst .

echo "this is a corrupted image file" > corrupt.img
gnoic -a leaf1 -u gnoic1 -p gnoic1 --skip-verify file put --file corrupt.img --dst /var/log/srlinux/corrupt.img
gnoic -a leaf1 -u gnoic1 -p gnoic1 --skip-verify file remove --path /var/log/srlinux/corrupt.img

All four work. So gnoic1, whose job is backups, can also upload whatever it likes to the switch. Time to fix that.

4.2

Allow backups, deny uploads with an Authz policy

An Authz policy names principals (users or roles) and the RPC paths they may or may not call. This one lets gnoic1 stat and get files, and denies put:

{
  "name": "Ext-clients",
  "allow_rules": [{
    "name": "backup-access",
    "source":  { "principals": ["gnoic1", "gnoi-clients"] },
    "request": { "paths": ["/gnoi.file.File/Get", "/gnoi.file.File/Stat"] }
  }],
  "deny_rules": [{
    "name": "backup-access",
    "source":  { "principals": ["gnoic1", "gnoi-clients"] },
    "request": { "paths": ["/gnoi.file.File/Put"] }
  }]
}

Install it with Authz Rotate. The command carries the same policy as one escaped string:

VM shell
gnsic -a leaf1 -u admin -p NokiaSrl1! --skip-verify authz rotate --policy "{\"name\":\"Ext-clients\",\"allow_rules\":[{\"name\":\"backup-access\",\"source\":{\"principals\":[\"gnoic1\",\"gnoi-clients\"]},\"request\":{\"paths\":[\"/gnoi.file.File/Get\",\"/gnoi.file.File/Stat\"]}}],\"deny_rules\":[{\"name\":\"backup-access\",\"source\":{\"principals\":[\"gnoic1\",\"gnoi-clients\"]},\"request\":{\"paths\":[\"/gnoi.file.File/Put\"]}}]}"
You should see
INFO[0000] "leaf1:57400": got UploadResponse
INFO[0001] "leaf1:57400": sending finalize request
INFO[0001] "leaf1:57400": closing stream

Check that the switch has it:

VM shell
gnmic -a leaf1 -u admin -p NokiaSrl1! --skip-verify --encoding json_ietf \
  get --path /system/aaa/authorization/authz-policy
Still the default policy?

gnsic is beta software and doesn't always push the policy on the first try. Run the rotate command again.

4.3

Test the policy, then remove it

Repeat the stat, get and put from 4.1. Stat and get still work. Put does not:

Expected refusal

On the dashboard

Remove the policy before moving on, so the next exercises aren't blocked:

4.4

Give leaf1 a certificate you can trust

With Certz the switch generates its own key and a signing request. Only the signed certificate travels back, so the private key never leaves the box. The flow:

  1. create a TLS profile on the switch
  2. create a CA on your VM
  3. check the switch can generate a CSR for your key type
  4. rotate: the switch creates the CSR, your client signs it, the switch installs the certificate
  5. point the gRPC server at the new profile
VM shell
# 1. a new TLS profile, and the list of profiles
gnsic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure certz add-profile --id Corp-Sec-A
gnsic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure certz get-profile-list

# 2. a CA of your own: ca.pem and ca.key (RSA 2048, SHA-256)
containerlab tools cert ca create
openssl x509 -in ca.pem -noout -text | head -n13

# 3. can the switch make a matching CSR?
gnsic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure certz can-gen-csr --cn leaf1 \
  --csr-suite CSRSUITE_X509_KEY_TYPE_RSA_2048_SIGNATURE_ALGORITHM_SHA_2_256
You should see
INFO[0000] leaf1:57401: added profile "Corp-Sec-A"

| leaf1:57401 | Corp-Sec-A        |

| leaf1:57401 | true             |
VM shell
# 4. CSR on the switch, signed by your CA, installed in the profile
gnsic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure certz rotate \
  --cn leaf1 --dns leaf1 --san-ip-address "172.20.20.2" \
  --ca-cert ca.pem --ca-key ca.key \
  --csr-suite CSRSUITE_X509_KEY_TYPE_RSA_2048_SIGNATURE_ALGORITHM_SHA_2_256 \
  --id Corp-Sec-A --version 2
You should see (shortened)
INFO[0000] leaf1:57401: can generate CSR
INFO[0000] leaf1:57401: returned CSR:
    Subject: CN=leaf1
    …
INFO[0000] leaf1:57401: upload response: certificates:{}
INFO[0000] leaf1:57401: sending finalize request
Certz says "Unauthenticated"?

If your gnsic build refuses the insecure port, send the same commands to the TLS server instead: replace -a leaf1:57401 … --insecure with -a leaf1 … --skip-verify.

4.5

Switch the gRPC server over and connect securely

VM shell

  get --path /system/tls/profile[name=Corp-Sec-A]

# 5. the secure server uses it from now on
gnmic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure \
  set --update-path /system/grpc-server[name=mgmt]/tls-profile --update-value Corp-Sec-A

Now the real test. No --insecure, no --skip-verify: your client checks the switch's certificate against your CA. Because the certificate lists both the name and the management IP, both work.

You should see

Section 5 · gRIBI

Steer traffic by programming the RIBgRPC Routing Information Base Interface

gRIBI lets a controller install routes as if a routing protocol had learned them: next hops, next-hop groups and prefixes, acknowledged once they are in the RIB and the FIB. You'll move leaf1's traffic to leaf2 off the spine and onto a direct link that no routing protocol knows about.

On the dashboard

5.3

Inject the route

The payload in grib-input.yml builds the route bottom-up, and the order matters: a next hop, a next-hop group that uses it, then the prefix that points at the group.

default-network-instance: default
params:
  redundancy: single-primary   # only the primary client may change routes
  persistence: preserve        # routes stay after the client disconnects
  ack-type: rib-fib            # answer once the route is in RIB and FIB
operations:
  - op: add
    election-id: 1:0
    nh:  { index: 1, ip-address: 172.16.10.1 }
  - op: add
    election-id: 1:0
    nhg: { id: 1, next-hop: [ { index: 1 } ] }
  - op: add
    election-id: 1:0
    ipv4: { prefix: 2.2.2.2/32, nhg: 1 }
VM shell · in gribi
gribic -a leaf1:57401 -u admin -p NokiaSrl1! --insecure modify --input-file grib-input.yml
You should see, three times
response: result: {
  id: 1
  status: FIB_PROGRAMMED
}

Programming the FIB can take ten seconds or so.

Client flags you'll type all day

  • -a leaf1:57401 --insecure: plain-text server, no TLS
  • -a leaf1 --skip-verify: TLS on 57400, certificate not checked
  • --tls-ca ca.pem: TLS, certificate checked against your CA
  • --encoding json_ietf: readable JSON with module prefixes
  • --type config: configuration instead of state on Get

Paths

  • Keys select list entries: /interface[name=ethernet-1/1]
  • Wildcards work in keys: [name=ethernet-*], [name=*]
  • OpenConfig paths start with openconfig:/
  • Find any path: pwc xpath in the CLI, or the YANG Browser
  • Limit big answers with --depth

When something fails

  • connection refused: check host and port, and that the lab is up (sudo clab inspect --all)
  • tls: failed to verify certificate: add --skip-verify, or use --tls-ca
  • PermissionDenied: the user's role or an Authz policy forbids the RPC
  • No such file: run file-based commands from the repository folder
